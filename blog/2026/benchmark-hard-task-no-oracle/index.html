100 秒被秒杀之后：我们把 benchmark 升级成了"没人会做的题"

TL;DR：

  • 我们出的第一道”hard 题”被当代前沿模型（DeepSeek-V4.1-Flash 驱动的 claude-code）107 秒解出，补跑 5 次全部通过（86–118s）——难度设计翻车；
  • 复盘找到三个”直白”：性能信号无歧义、bug 修复面只有一行、核心线索能被 objdump 直接读出来；
  • 于是第三道题换了物种：开放式性能题——32 张国产 GPU 上把 27B 模型的训练吞吐从团队实测纪录 85.9 推到 ≥87.0 TFLOP/s/GPU，没有 oracle，因为出题团队自己还没解出来；
  • 这篇讲：校准翻车复盘 + 难题设计 + 以及这题里真正的工作量——六层反作弊判分器。

1. 战报：103 秒，五连杀

先交代背景。我们在做一个国产 infra 方向的 agentic benchmark（Harbor 格式），目标是给 AI agent 出”真实工程难题”。前两道题做完、判分器双冒烟（裸环境 0.0 / oracle 1.0）全绿之后，搭了一条完整的自动化评测链路：harbor 起容器 → agent 解题 → 判分 → 汇总通过率，记忆隔离（每 trial 干净副本 + 全新容器 + 独立会话）也做了。

然后拿第二道题（GEMM 静默回退，我们定为 hard）跑了第一次真实校准：

trial 1:  reward=1.0   用时 107s
5 trials: 5/5 通过，86–118s，均值 103s

怕它是撞运气，把 339KB 的轨迹逐条翻了：20 次 Bash、15 次 Read、3 次 Edit——是真诊断。读代码结构 → 复现慢 baseline → objdump -d 反汇编扩展的 PyInit 入口 + readelf 看段（真的在分析 PEP 489 多阶段初始化的二进制特征）→ 写探针验证 sys.modules 行为 → 修 loader → 重跑验证。证据链完整，判分没洞。

题没问题，是题太简单。

2. 复盘：好题的三条反例

为什么 100 秒就能破？题目设计踩了三个”直白”：

  1. 性能信号无歧义：651ms vs 48.5ms 的 16 倍差距摆在脸上，profile 一眼就定位到 dispatcher 回退，不需要跨日志交叉关联；
  2. bug 修复面极小：找到”只认自注册扩展”的判断就完了，改一行；
  3. 核心线索可被标准工具直接读出：PEP 489 是公开知识，objdump/readelf 能把”cublas 不自我注册”这个核心证据拍在 agent 脸上——等于谜面自带答案。

由此得到出题的反面清单：证据必须藏在”工具帮不上忙”的地方，或者干脆不埋 bug。前者比如”五次失败日志的交叉关联”（grep 不出来，要读进去理解）；后者就是第三题的形态——

3. 第三题：连出题人都没做出来的题

题面：4 节点 32 卡国产 GPU（沐曦 C550）集群，27B 模型，把训练吞吐从团队实测纪录 85.9 TFLOP/s/GPU 推到 ≥87.0。

这道题和前两道有本质区别：

  前两题 第三题
形态 埋好的 bug，找到即修复 开放式性能题，没有预设答案
最优解 已知（一行修复） 未知——我们自己也还没解出来
agent 要做什么 诊断 诊断 → 提出优化 → 实现 → 在真集群上实测迭代
时长量级 分钟级 目标是 8h+，甚至做不出

线索全是真实遗留物：失败尝试的配置和日志、一个已被回滚的部分重算补丁（需要 agent 自己重新实现）、OOM 现场、驱动层 SIGSEGV 记录。没有一样东西写着”答案在这”——它就是把我们团队过去几周真实的优化战场原样端给 agent。

为什么说这是难题的终极形态：我们团队（天天干这个的人）做到 85.9 之后也卡住了，87 这个目标是从树内方案投影出来的，还没实测达到过。如果 agent 做出来了，它比题更值钱；做不出来，题就成立。 两种结果都有产出。

4. 这题真正的工作量：判分器

开放性能题的题面一句话就说完了，工作量 90% 在判分——因为 verify 对象是”吞吐数字”这个最容易造假的东西。判分器做了六层：

  1. 独立重算吞吐：框架自报的 TFLOPs 与判分器从日志时间戳重算的值做一致性校验（1% 容差）——防止改打印代码虚报；
  2. 逐 iter 时间戳对拍：日志里每个 iter 的打印间隔必须和声称的 iter 耗时一致——防止伪造”跑得快”的日志；
  3. 墙钟交叉验证：判分器自己掐表 vs 日志声称的总跨度——伪造变快超过 10% 就抓；
  4. 运行中期硬件采样：判分中途对每块卡采样显存占用（>20GiB）——杀”假训练”（起了进程但没真跑）；
  5. loss 锚点：前几个 iter 的 loss 必须在参考值 ±0.05 内、辅助 loss 必须存在、不允许 nan/skip——防止用改数学换速度（比如偷偷关掉某些计算）；
  6. 集群卫生入分：判分前后所有节点所有卡必须全闲、无残留训练进程——agent 留烂摊子直接 0 分。这条是从真实运维规矩搬过来的。

外加 oracle 校准的设计巧思：把纪录配置（85.9 那套）当 oracle 交上去，期望结果应该是”审计项全绿、仅阈值一项红、reward 0.0”——一跑就知道六层审计有没有误伤合法优化。

5. 诚实声明

这道题的阈值 87.0 目前来自方案投影（修正版重算方案预计 ~88），不是实测值。发题前必须先自己解出来一次（把回滚的补丁重新实现 + 补齐缺失的注入逻辑），确认可达；如果实测最优到不了 87，阈值就下调到”最优 −1”。把没验证过的阈值发出去，是对做题人的不负责任。

另外承认一个判分盲区：在 agent 全权控制代码栈的前提下，亚百分级的时间戳伪造机械上无法完全检测，兜底手段是轨迹抽查——这是当前所有 agentic benchmark 的共同局限，写在这里算明牌。

6. 这三天学到的事

  • 先能量化通过率，再谈调难度。没有 calib 链路之前，”这题 hard”只是我们的自我感觉；链路通了之后，一句话就能证伪：”103 秒，五连杀。”
  • 难度不来自题面的复杂度，来自证据的埋藏深度。能被 grep/objdump 直接读出来的证据，对当代 agent 等于写在脸上。
  • 最难的题是没有标准答案的题。当出题人自己都不会做时，”会不会太简单”这个问题就自动消失了——剩下的唯一问题是判分器够不够硬。
