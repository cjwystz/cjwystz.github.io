MetaX TP overlap 排查记录：接口跑通之后，为什么 GEMM 反而变慢？

这几天我们在 MetaX 上排查了 TP 通信计算重叠（TP overlap）。工作分成两部分：先解决 TransformerEngine-FL 前端与旧版 MetaX 原生扩展的接口兼容问题，再解释为什么接口跑通后，部分权重梯度矩阵乘法仍然偏慢。

截至 2026 年 10 月 19 日，TransformerEngine-FL PR #139 已提交，仍开放、尚未合并。该 PR 只包含兼容性源码和回归测试。本文还记录了一套独立的 UB 分配实验及其训练短测，它不包含在当前 PR 中。

核心结果是：目标 UB 分配从 Uncache 改为 Global 后，隔离实验里的 Wgrad GEMM 耗时从约 10.6 ms 恢复到约 5.8 ms；单节点 TP4 训练短测观察到小幅收益，但四节点 27B 尚无可确认的净收益。 算子耗时、训练吞吐与上游修复范围需要分别解释。

基础知识：TP overlap 想隐藏什么开销

张量并行（TP）把一个大矩阵运算拆到多张卡上。计算被拆开后，部分算子需要拿到其他 rank 的激活，或把各 rank 的计算结果汇总。常见通信包括 AllGather（AG）与 ReduceScatter（RS）。

以需要完整输入的线性层为例，可以先把各 rank 的输入片段收集起来，再执行矩阵乘法。最直接的执行顺序是：

等待 AllGather 全部完成 → 执行 GEMM

如果算子和通信接口允许分块，就有机会让“后续输入分块的通信”与“已就绪分块的计算”同时进行。用理想化模型表示：

串行耗时 ≈ T_comm + T_compute
理想重叠耗时 ≈ max(T_comm, T_compute) + 调度与同步开销

这个式子只帮助理解上限。真实系统还要考虑分块是否足够大、依赖是否满足、通信与计算是否争用资源，以及数据进入 GEMM 的内存路径是否发生变化。

在这条执行路径中，Userbuffer（UB）是原生 overlap 实现使用的通信缓冲区及其管理对象。它不能简单等同于一个普通 PyTorch Tensor：其对象类型、分配方式、同步和底层 GEMM 接口都可能有额外约束。

反向传播中的权重梯度通常可写成：

Y = XW
 dW = Xᵀ · dY

这里将样本和序列维合并，省略 TP 分片和布局变换。它说明一个容易忽略的点：即使矩阵形状、数值与 GEMM 实现相同，X 来自哪条分配路径，也可能影响这次计算。 是否真的影响，需要控制变量证明。

第一层问题：前端与原生扩展的接口没有完全对齐

我们使用的前端路径与已测试的旧版 MetaX TE 扩展，在能力查询、枚举和 UB 对象接口上存在差异。不能因为接口名字相近，就默认二者兼容。

1. 能力查询需要真正到达 MetaX 后端

前端会查询 multicast 支持、原生 UB 是否使用 MPI 构建，以及 stream 优先级范围。修复补齐了三项查询的后端转发和注册：

device_supports_multicast
ubuf_built_with_mpi
get_stream_priority_range

新增注册同时检查 MACA 运行时标识与后端可用性。这避免普通 PyTorch 或其他厂商环境误选 MetaX 实现。这里做的是能力查询的接线，不能把“查询已注册”写成“所有能力都受支持”。

2. 相同枚举值，不代表相同原生类型

前端 overlap 枚举和扩展中的 CommOverlapType 可能属于不同类型。原生绑定接受参数时，光有相同整数值未必足够。

修复在调用原生构造函数前显式转换：

comm_type = tex.CommOverlapType(int(comm_type))

这样送到原生接口的是它自己定义的枚举。兼容层负责转换，避免让上层调用者了解扩展版本差异。

3. 为旧版 Userbuffer 补接口，同时保留原生对象身份

前端需要 with_cublasmp() 查询，而已测试的旧版 UB 类没有这个方法。MetaX 路径也没有实现这里的 cuBLASMp 功能，因此缺失时补充 False。

实现没有把原生对象包成任意 Python 代理，而是采用原生类的 Python 子类：

class LegacyUserbuffer(native_type):
    def with_cublasmp(self):
        return False

这是实现思路节选。实际代码会先检查原生类是否已有该方法：已有就直接使用，并缓存兼容子类。

保留原生类型关系，是为了满足下游 GEMM 对原生绑定对象的要求。补齐方法只是表层目标，不能因此破坏后续接口的类型兼容性。 同时，显式请求不支持的 cuBLASMp overlap 仍会被拒绝。

4. 原生模块加载后，要恢复前端占用的模块别名

另一处前置问题来自 sys.modules["transformer_engine_torch"]。前端 dispatcher 与厂商扩展的加载需要协调这个名称。

旧逻辑只有在扩展加载时自行注册了该名称，才恢复原来的对象。但在已测试的不同构建中，自注册行为不同：torch 2.8 构建会注册，torch 2.10 构建不会。因此“旧构建正常”没有证明恢复逻辑完整。

修复在 finally 中按加载前状态恢复，覆盖成功与异常路径：

if saved_owner is not None:
    sys.modules["transformer_engine_torch"] = saved_owner
else:
    sys.modules.pop("transformer_engine_torch", None)

PR #139 包含 #135 的这项前置修复，不用于关闭或替代 #135。上述源码与回归测试见 #139 完整改动。

第二层问题：AllGather 结束了，Wgrad GEMM 为什么仍然慢

接口跑通之后，排查重心转向性能。最初容易想到的解释是：通信和计算同时执行，争用了资源，所以 GEMM 变慢。

但前期隔离实验发现：即使先等 AllGather 完成，再让部分 Wgrad GEMM 读取目标 UB 输入，耗时仍然偏高。 这说明“正在通信时的资源竞争”不能单独解释该现象。

我们对比了三条输入路径：

前期隔离对照 所测 GEMM 耗时 解释边界
直接读取目标 UB 输入 约 10.6 ms 目标路径上的异常耗时
复制到普通显存后再计算 约 5.7 ms 不含复制成本，不能直接当作训练优化收益
目标分配改为 Global，不加输入 copy 约 5.8 ms 支持分配路径是重要影响因素

复制实验的用途是诊断：在数值和后续计算相同的情况下，更换输入存储路径能否改变结果。它不是免费优化，因为 copy 也消耗时间、带宽和显存。

进一步检查发现，在所排查的原生库版本中，目标分配携带 Uncache 标志。将该分配的 flags 从 5 改为 1（Global） 后，无需额外输入 copy，GEMM 耗时也恢复了。

这些结果支持继续检查分配策略，但还不能断言某一级 cache 或某个底层物理机制已被完全定位。Uncache / Global 是这里的分配标志；从名称直接推导硬件行为，仍然缺少证据。 表中是前期消融记录，不是后面训练短测重新采集的 profiling。

为什么先用进程内拦截器验证

当时没有拿到与安装版本匹配的 MetaX 原生分配源码，也没有找到直接设置目标策略的公开接口。为了先回答“改变分配策略是否有用”，我们做了一个可选的 C 动态库拦截器。

它只在自有训练进程中识别特定 UB 数据缓冲的分配，把目标参数从 Uncache 改为 Global，再交给原来的 MetaX 分配函数。Python 工具负责构建、启动和检查。

这套实验方案的范围很窄：

  • 没有修改磁盘上的共享库文件，也没有额外复制输入
  • 工具默认关闭，依赖特定原生库版本与调用位置
  • 目标数据缓冲与控制分配需要分别审计，不能把所有分配一律改成 Global
  • 完整 guard.py run GPU 包装尚未验证；真实 GPU 短测使用构建工具加独立实验 launcher

它适合验证假设，还不能代替正式的后端接口。长期更合理的方式，是由原生库提供受支持的 UB 分配策略入口，并明确适用条件。

最新 TP4 训练短测：小幅收益，但对暖机窗口敏感

算子耗时恢复后，还需要回到训练。GEMM 快了，不代表每一步训练都按相同比例变快。

这轮单节点实验的共同设置为 4 卡、4B 模型、TP4/PP1/DP1、seq2048、GBS16、MBS1、BF16、seed42。模型、数据及其他训练控制保持一致，按 ON → OFF → ON 顺序分别运行 10 步。

ON 使用 Global 分配实验方案，保留前向 AG overlap，关闭 bulk_dgrad、bulk_wgrad 和 RS overlap。OFF 关闭 TP overlap。三组都不额外加入输入 copy、profiler 或 checkpoint 保存。

配置 第 3–10 步平均耗时
ON A 7.179 秒/步
OFF 7.374 秒/步
ON B 7.212 秒/步

两次 ON 合并后的平均值是 7.19536875 秒/步。在每步工作量相同的条件下：

吞吐提升 = T_OFF / T_ON − 1
         = 7.3740875 / 7.19536875 − 1
         ≈ 2.48%

对应的平均单步时间下降约 2.42%，两个百分比的分母不同，不能混用。

三组统一改看第 4–10 步时，吞吐差变成约 1.31%。因此目前更稳妥的结论是“短测观察到小幅收益，且对暖机窗口敏感”，尚不足以证明稳定长期收益。ON 同时改变了 overlap 和分配策略，也不能将全部训练收益单独归因于 Global。

三组共 30 步正常结束，NaN/skipped 为 0。ON 的 4 个 rank 都记录到真实原生 UB AG 调用，OFF 的 UB 调用为 0，交付源码哈希保持不变。但进入 overlap 调用路径，不等于本轮已经用时间线证明通信与计算实际重叠；这轮没有启用 profiler。有限 loss 与无 NaN 也不能替代完整梯度数值对照。

四节点 27B 的此前短测与历史基线差异不足 1%，暂时没有可确认的净收益。模型规模、并行拓扑和瓶颈都会变化，不能把单节点结果直接推广过去。

这次排查中最有用的习惯

先把接口正确性和性能拆开。 能创建 UB 对象，只证明兼容性的一部分；是否真正进入原生执行路径、结果是否正确、训练是否更快，需要独立证据。

把通信完成作为一个控制条件。 等 AG 完成后性能问题仍在，就需要继续查输入存储、布局与分配路径，而不是把全部异常都归结为 overlap 资源竞争。

回到固定工作量的训练比较。 copy 后 GEMM 更快、某个算子恢复到 5.8 ms，都不能直接换算成端到端收益。训练短测还要检查暖机敏感性、路径是否生效以及跨规模是否成立。

本文依据 10 月 16 日简版说明、候选包测试记录和当前 PR 整理。OpenAI Codex 协助核对源码、整理证据与撰写；没有为这篇文章重新启动 GPU 实验。
