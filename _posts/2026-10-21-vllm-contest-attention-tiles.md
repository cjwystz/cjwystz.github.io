这篇在 10 月 23 日补记，整理前几天准备 FlagOS 推理赛道时的一次实验。工作围绕 MiniCPM5-2B、vLLM 插件和 FlagGems 的分页 Attention 展开，先从一个范围较小的 prefill 分块调整开始。

目前比较有用的收获，是把数值参考、独立算子测试、真实模型检查和请求吞吐对照接了起来。下面记录的是开发过程与当前配置下的观测，尚未完成正式精度评测和完整比赛流程。

## 1. 先把实验范围收窄

本次使用 BI-V150 32 GiB，框架沿用比赛分支与 FlagGems 5.3.5。Attention 小测采用 BF16、16 个 Query heads、2 个 KV heads、head dimension 128、每页 16 个 token。

我主要调整两个执行参数：Query/head 展开后的行分块大小，以及每个程序实例使用的 warp 数。分页寻址、因果可见性和计算精度保持在同一个比较范围内，纯 decode 路径没有顺带改成新的 prefill 配置。

这里有个容易误读的地方：`BLOCK_M=64` 不代表这个布局每块处理 64 个不同的 token。16:2 的 GQA 配置中，一组 KV 对应 8 个 Query heads；本次展开布局下，BM16 和 BM64 分别对应每块 2 和 8 个 Query token。读 kernel 参数时，需要先还原索引与张量布局。

## 2. 第一次参考检查没有通过

开始计时前，我用固定输入和独立 FP32 参考检查输出。第一份未修改 kernel 的小测没有通过，归一化 RMS 误差约为 19.6%，因此那次运行没有被拿来比较优化收益。

随后把在线 softmax 的状态拆开检查：行最大值、分母以及除法前的累加器分别与参考比较。当前环境中观察到的主要偏差，是分母比参考多约 1。

这还不足以说明原始公式写错了。原代码使用 `M=-inf, L=1`；若第一次重缩放的 `alpha=0` 正确执行，初始的 1 应被消去，与无 sink 路径的零初始化等价。**目前没有查清这一环境下偏差的精确编译原因。**

为了继续隔离分块本身的影响，后续在独立副本中，让所有对照和候选采用相同的无 sink 零初始化处理，并重新冻结输入、源码和门槛。集成路径的页表尾部读取掩码也在两边保持一致。这些共同处理属于比较前提，不能算成某一候选独有的优化。

这个检查没有覆盖带 attention sink 或其他分段实现的全部路径，也不作为面向所有模型的通用修复结论。

## 3. 先比较独立算子

小测包含短序列、尾页、首个 chunk、4K/16K 上下文、混合长度、分块边界与纯 decode 等 8 个用例。输出区预填 NaN，尾部放 canary，另外检查无效页和未使用位置，避免只比较一小段正常输出。

在冻结的用例与容差下，各候选均通过检查；候选与统一处理后的对照，完整输出逐元素相同。长 Query 的 FP32 参考比较使用每条序列固定抽取的 32 行，短 Query 检查全部行，最大归一化 RMS 约为 0.2332%。这仍然是有限用例的结果。

下面两项都是 **2048 个 Query token 的 chunk**，其 KV 长度分别为 4096 和 16384，并非一条完整请求的首 token 延迟。

| 配置 | 当前布局每块 Query token | 4K 上下文中位耗时 | 16K 上下文中位耗时 |
|---|---:|---:|---:|
| BM16 / 4 warps，对照 | 2 | 15.255 ms | 75.301 ms |
| BM32 / 4 warps | 4 | 8.880 ms | 43.867 ms |
| BM64 / 4 warps | 8 | 6.821 ms | 33.387 ms |
| BM64 / 8 warps | 8 | 5.478 ms | 26.279 ms |

每项预热 3 次，进行 5 轮交错测量，每轮每配置调用 10 次。编译、参考计算与 profiler 采集不进入事件计时。

在这组条件下，BM64 / 8 warps 的独立算子耗时约为对照的 1/2.78 和 1/2.87。更大的行分块可能改善数据复用与工作组织，但实际原因还受硬件、寄存器和共享内存等因素影响，不能把一次参数选择当成跨设备最优值。

## 4. 确认模型真正调用了新路径

独立 kernel 能运行，还需要确认真实模型调用的是同一个实现，并且实际 stride 与人工连续张量的假设一致。

集成检查覆盖了实际交错 K/V 页、带间隙的 Query/output 行布局和边界保护。完整模型另用固定 4K、16K 输入，各生成 16 个 token：两边的生成 token 相同，所检查生成 token 及 top-5 logprobs 的最大差值为 0。

短 profiling 窗口还记录了真实 launch grid。16K prefill 的每边 8 个执行 step 内，均捕获 336 次目标 Attention 调用；该窗口的 Attention 累计 GPU 时间由约 12.795 秒变为 4.564 秒。

这些记录可以支持“目标路径已命中、所检查的模型输出一致”，不能代替整套精度评测；采样窗口里的算子时间比，也不能代替整轮请求吞吐比。

## 5. 完整请求规模的单轮开发对照

之后把候选接入模型，对两个输入长度分别完成一轮完整请求数量的开发 A/B：

| 场景 | 输入 / 输出长度 | 每边请求数 | 并发上限 |
|---|---|---:|---:|
| 4K | 4096 / 1024 tokens | 256 | 64 |
| 16K | 16384 / 1024 tokens | 128 | 64 |

两边都使用独立新启动的服务；同一场景的 serve 参数与实际 worker 配置一致。纳入比较的日志没有额外 warmup 请求，也没有继承另一场景的前缀缓存。中途被停止的旧 16K 测量没有拼进汇总。

| 场景 | BM16 / 4 warps 总 tokens/s | BM64 / 8 warps 总 tokens/s | 观测变化 |
|---|---:|---:|---:|
| 4K | 1551.85 | 1965.95 | +26.68% |
| 16K | 873.06 | 1524.03 | +74.56% |

这里沿用 benchmark 的 **Total tokens/s**，计入输入与输出 token，不是只统计新生成 token。两边全部请求完成、零失败；4K 没有抢占，16K 两边均记录了 4 次抢占。

对应的平均 TTFT，4K 为 15.125 秒与 9.318 秒，16K 为 621.266 秒与 335.911 秒。这是并发 64、长请求压力下的请求级观测，包含等待与调度，不能读成单请求 Attention 的计算时间。

最重要的比较边界有三点：

- **对照和候选都包含同样的数值处理与页表掩码处理**，所以比较隔离的是分块变化，不是相对完全未修改官方版本的收益
- **每个场景、每边仅完成一轮**，当前数据不能估计运行间方差，也不是官方四轮汇总成绩
- **尚未运行 MATH-500 正式精度门**，短输出与 logprob 检查不能替代它

后续如果继续投入，应先完成正式精度评测，再按一致缓存初态和完整协议重复测量。扩大 workload 或换设备后，原来的分块选择也需要重新检查。

## 6. 这次暂时记下的方法

对我而言，这次最值得保留的是检查顺序：先确认当前输入与参考一致，再比较算子；确认模型实际使用了它，再比较请求级指标。前一层通过，只是进入下一层验证的条件。

后面的 profiling 也出现了正确但更慢的候选，以及 kernel 之外的主机侧等待。我把这些另记在[后续排查笔记](/blog/2026/vllm-contest-profiling-notes/)，避免只保留一次有提升的结果。
