TL;DR：

- 上一篇那道"连出题人都没解出来"的开放性能题，先在小规格上做了第一次真 agent 校准：**4h budget 跑满、AgentTimeoutError、零交卷、reward 0.0**；
- 但翻完 3079 条轨迹：这不是躺平——双峰振荡诊断、MCCL 隔离基准实锤通信串行化、实测试到 **~36.8 TFLOP/s/GPU（基线 24–25，+47%）**，离阈值 40 只差 ~3.2；
- 绊脚石有两个：一个算我们的（agent 改的入口文件根本没被 launcher 加载，环境透明度问题），一个算它的（num_workers 调参打偏 loss 锚点且没提速）；
- 结论：**阈值 40 不降**，修好坑一后补跑 3 个 trial；判分协议改一条——记 best-checkpoint 连续分，不只看 binary。

## 1. 战报：4 小时，0.0，零交卷

先补一个上一篇没交代的设定：那道"27B / 85.9 → 87.0"的题其实有个小规格姊妹题——**Qwen3.5-4B、FlagScale、沐曦 GPU**，优化目标是把训练吞吐从基线 24–25 TFLOP/s/GPU 推到 **≥40**（约 1.6 倍）。小题用来快速校准，免得一上来就烧 32 卡的预算。

第一次真实 agent 运行（DeepSeek-V4.1-Flash 驱动的 claude-code，4h budget）：

```
reward:      0.0
终止方式:    AgentTimeoutError(4h 跑满)
提交:        无(零交卷)
轨迹:        3079 条
最好成绩:    ~36.8 TFLOP/s/GPU(基线 24–25,+47%;距阈值 40 还差 ~3.2)
```

单看 reward 是完败。但上一篇说过，这道题两种结果都有产出——所以我把 3079 条轨迹翻了一遍。

## 2. 不是躺平：轨迹里的真实工作

三件事说明它是真在干：

**隔离规则全程守住。** 所有改动只在 `zzy_work/mywork` 副本里，原树零接触。上一篇判分器第六层"集群卫生入分"是从真实运维规矩搬来的，这条没白设计。

**诊断方向专业，而且路径是教科书级的：**

1. 发现 iter 时间**双峰振荡**：1723–1880ms 与 2400–2600ms 两档交替出现，且是数据确定的、不是抖动——说明它区分了"噪声"和"结构性信号"；
2. 做了 **MCCL 隔离基准**：8.65GB fp32 ReduceScatter 单独跑只要 40.7ms，但训练里同一通信要 740ms——据此提出"通信被串行化"的假设。先隔离测量、再对比定位，这就是人类性能工程师的标准动作。

**实测有真实进展。** 试到的最优吞吐 ~36.8 TFLOP/s/GPU，+47% 不是纸面数字，是在真集群上跑出来的。离 40 差 3.2，题确实卡在 frontier 上——这正是我们设计它时想要的状态。

## 3. 两个坑：一个算我们的，一个算它的

时间耗光不是因为探索本身慢，是被两个坑吃掉的。这两个坑性质完全不同，必须分开记账。

### 3.1 坑一（算我们的）：改了文件，但跑的不是它

DS 花了不少时间改自己副本里的 `train_qwen35.py`，但 launcher 启动时会 **cd 进原树**执行 `./flagscale/train/megatron/train_qwen35.py`——editable install + launcher 的路径解析，让"改自己的副本"这件事并不直接。它改的入口文件**根本没被加载**，真正生效的只有通过 PYTHONPATH 注入的 `training.py`。

它后来意识到了这一点，准备去修 entrypoint（需要搞懂 MetaPathFinder 的注入机制），但时间已经不够了。

这类摩擦在 FrontierSWE 的 QA panel 里会被单列为 task-induced friction，不计入模型能力——它测的是"能不能读懂 editable install 的加载链"，而不是"能不能优化吞吐"。**这是题的环境透明度问题，记在我们头上，修题。**

### 3.2 坑二（算它的）：num_workers 调参，打偏锚点还没提速

另一条路是它自己走岔的：调 `num_workers` 不但没提速，还把 loss 锚点打偏了（12.954 vs 参考 13.019，超出 ±0.05 容差）。判分器的 loss 锚点层防的就是"用改数学/改数据路径换速度"，这一抓是判分器在正常工作。

白试一条路的成本记在它自己头上。这类试错**该保留**——它区分的正是"会调"和"不会调"。

## 4. 校准结论

**阈值 40 保持不动。** DS 到 36.8 说明方向可达、题不是死题；差 3.2 说明它确实卡在 frontier 上。降到 35 就会把一道能区分头部模型的题降级成中档题，不划算。

**按优化面分档，不按阈值分档。** 4B 题的优化面在通信串行化（那个 740ms 的 MCCL），27B 题的在 partrecomp/selrecomp 重算方向——两题信号正交，各测一种能力，比"同一题两个难度档"信息量大。

**修好坑一再补跑 3 个 trial**（`run_trials_t4b.sh 3`），确认 36.8 是可复现还是单次运气。延长 budget 到 8h 暂时不做——这次时间是被坑吃掉的，不是被问题本身吃掉的，坑修了之后 4h 可能够。

**判分协议改一条：记 best-checkpoint 连续分，不只看 binary。** 36.8/40 ≈ 0.92 和"完全没动"在 0/1 计分下都是 0，但信息量天差地别。上一篇拆 FrontierSWE 时我们吐槽过它没披露"无提交 trial 怎么计分"——现在我们自己的 agent 也零交卷了，这个问题从别人的缺口变成了自己的待办。

## 5. 诚实声明

- **n=1。** 36.8 是单 trial 结果，稳定性未验证，补跑之前一切都只是" calibration 的初步读数"；
- 轨迹分析是人工读的（3079 条），归因可能有漏；
- 坑一到底吃掉多少时间，没法从轨迹里精确切分，"不修它会怎样"无从得知——所以只能修完再跑，用对照回答。

## 6. 学到的事

- **超时不是单一失败模式。** 躺平、卡死、真干没干完，三种超时对题目的含义完全不同。这道题属于第三种——意味着题成立，而且 agent 的能力边界恰好落在阈值附近；
- **环境摩擦力会污染难度信号。** 如果不修坑一就再跑，3 个 trial 大概率卡在同一处——那测的是坑的复现性，不是模型的稳定性；
- **"继续探索还是见好就收"是当代 agent 的通病。** DS 这次零交卷，和 FrontierSWE 榜上那些"打算提交但一直干到预算耗尽"的模型是同一类失败。submit 机制（记录后可继续改、已交不丢）必须前置到题面里讲清楚，否则我们在为模型的"不交卷习惯"而不是"能力不足"记 0 分。
