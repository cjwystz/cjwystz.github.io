这篇在 10 月 23 日补记，整理 10 月 21 日至 22 日的几项后续工作。前一篇写了 [Attention 分块的开发对照](/blog/2026/vllm-contest-attention-tiles/)，这次主要记录没有带来改善的候选，以及还没有完成闭环的排查。

这些记录暂时没有增加新的端到端优化收益。写下来，是为了以后能分清哪些方向试过、哪些只形成了线索，避免把同一件事重复猜几次。

## 1. KV 分块加大后，数值正确但更慢

在 BI-V150 上，保留此前 BM64 / 8 warps 的配置，仅把 KV tile 从 32 调整到 64。我原本想检查更大的读取与计算分块能否减少循环开销。

8 个固定数值用例均通过，没有放宽门槛。但耗时没有改善：

| 独立 kernel 场景 | KV tile 32 | KV tile 64 | 耗时变化 |
|---|---:|---:|---:|
| 4K chunk | 5.316 ms | 5.731 ms | +7.79% |
| 16K chunk | 25.143 ms | 26.881 ms | +6.91% |
| 混合长度 | 25.338 ms | 27.034 ms | +6.69% |

这轮用了更多预热，并以 ABBA / BAAB / ABBA 顺序做交错计时；事件计时与实际 kernel trace 的方向一致。因此没有把这个候选接入完整模型继续跑。

编译信息中，寄存器数从 102 增到 121，共享内存从 33,024 增到 49,664 字节，两边都未记录 spill。它们是有用的现象，但**资源用量增加本身，不能证明 occupancy 或某类访存等待就是根因**。没有相应硬件计数器时，我只把原因保留为待验证解释。

## 2. 少做一点 mask，也不一定更快

第二个候选保留原来的 KV 循环与 softmax 累加顺序，只对已经完全可见的前缀块增加一致分支，跳过逐元素因果比较。

原有 8 个用例加上 9 个短 Query / 长前缀边界用例，共 17 例通过；与现有实现的输出逐元素相同。但三个场景的耗时仍增加约 0.97%–1.37%，因此也没有接入模型。

“减少了一条比较”只是源码层面的描述。分支、编译器生成的指令、调度和资源使用都可能变化，最终还是要看当前输入和硬件上的测量。这两次尝试都提醒我：推测可以指导选候选，不能替候选通过性能验证。

## 3. 一段慢尾，把注意力引向了主机端

在 4K 请求场景里，满批运行之后的缩批尾段比较慢。初步采样看到部分时段 GPU 较空闲，但已有 decode trace 只展示 CUDA Graph 的聚合 launch，没有展开图内模型算子。

因此，我没有直接把 trace 中可见的 sampler 或 top-k 排名解释成“完整模型热点”，而是补了 CPU 栈、模型入口时间，以及配置查询路径的记录。

一波 64 个请求的仪器化诊断完成了全部请求。缩批观察窗口覆盖 125 轮，记录到：

- `execute_model` 累计主机墙钟时间约 64.436 秒
- 其中 32 次索引新 shape 的 overload miss，嵌套耗时约 62.438 秒
- CPU 栈进入 FlagGems 配置缓存，再进入 SQLAlchemy 的数据库反射路径

第二项包含在第一项里，**两者不能相加**；它们也不是 GPU kernel 时间，不能全部称为 Triton 编译时间。

当前源码中，新 shape 会对应不同配置表名，缓存未命中时可能反射整个数据库。一个范围较小的候选，是把反射限制为当前目标表，保留原有配置内容、算子实现和服务参数。

## 4. SQL 候选目前只通过 CPU 检查

隔离检查构造了 32 张无关表和两张有外键关系的表，比较已有表、缺失表、字段内容、创建、读取、更新与 fresh instance 的行为。

原路径查询已有目标时会反射全部 34 张表；候选限制为目标表。相关 CPU 语义检查通过，但这只能说明被检查的数据库行为一致。

**本轮尚未运行这个 SQL 候选的 GPU 模型输出检查和性能 A/B。** 因此，62 秒的嵌套观察值不能被写成“已经消除了62秒”，也不能据此换算整轮吞吐提升。

如果后续继续验证，两边应使用同一持久缓存快照的独立副本，冻结数据库、源码与服务初态，再先检查模型输出。否则缓存是否已被填充，可能比这次代码变化更影响结果。

## 5. C500：这次四轮没有复现历史 OOM

另一条工作是排查 C500 上此前出现的第三轮主机内存 OOM。这里重新运行的是当前安装版本的原 MM 路径，不是上面 BI-V150 的候选，也没有做优化前后对照。

10 月 22 日晚，原版路径完成 4K case 四轮，每轮 256 个请求，输入4096、输出1024 tokens、并发上限64；全部请求成功，新增 cgroup OOM kill 为零。

| 观测项 | 本次记录 |
|---|---:|
| 容器主机内存上限 | 48 GiB |
| 启动期主机内存峰值 | 43.958 GiB |
| 第一轮内存峰值 | 41.203 GiB |
| 第四轮内存峰值 | 41.240 GiB |
| 新增 cgroup OOM kill | 0 |

这些是容器主机内存，不是GPU显存。这次运行没有再次顶到上限，内存峰值有小幅增长；它不足以证明更长时间运行不存在泄漏。

历史 OOM 记录仍然成立，最后一段内存增长的来源也没有确定。我没有因为一次未复现，就把问题标成已经修复。导入链审计能证明部分模块导入会触发 GPU runtime 初始化，却不能单独证明某一大块匿名内存都由这个调用产生。

这次核心的请求结果、内存采样和源码冻结检查完成；附加 metrics 采集与退出守卫则保留了错误记录。测量完成和外围脚本存在问题是两件需要分别记录的事，不宜用一句“全部通过”合并掉。

## 6. 给下一次实验留下明确起点

目前保留的判断比较有限：扩大 KV tile 和增加 prefix 分支，在本次隔离用例上没有收益；缩批诊断找到了值得单独验证的主机侧路径；C500 这次四轮没有复现历史 OOM。

下一步若继续，应分别完成 SQL 候选的模型数值门与独立性能对照，并对历史 OOM 的内存增长来源补采样。不同设备、不同候选和不同运行初态的数字，不放在同一张“优化前后”表里。

对这类推理实验，我还在练习把三句话分清：看到了什么、目前能解释什么、下一次如何证伪。把负结果和没有闭环的部分保留下来，后面接着做会更清楚。
